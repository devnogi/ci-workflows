# Spring reusable CI and production deployment

The shared workflows run in the calling service repository. Call them by the full reviewed `ci-workflows` commit SHA. Configure private reusable-workflow access in GitHub and grant `contents: read`. No service or production workflow is activated by this repository alone.

## Interface

`spring-ci.yml` requires string inputs `service-profile`, `image-name`, `dockerfile`, and `compose-file`. Profiles are `base`, `auth-mysql`, `community-redis`, and `batch`. CI runs the caller's `scripts/secret-scan.mjs`, Gradle `verify`, profile-specific integration tests, report upload, a non-pushing Docker build, and synthetic production Compose rendering. Auth uses four isolated MySQL 8.0.42 instances and retains the current origin/dev MySQL test groups; Community uses Redis 7.4.9.

`spring-prod.yml` requires those four inputs plus `health-timeout` and `platform`. Use a timeout in seconds from 1 to 600 and `linux/amd64`. The production jobs read `PROD_COMPOSE_SERVICE`, `PROD_CONTAINER_NAME`, `PROD_REMOTE_DIR`, `PROD_HEALTH_URL`, and `PROD_COMPOSE_FILE` directly from the caller repository's `production` Environment variables. This is intentional: GitHub does not allow the `vars` context in a reusable-workflow caller's `jobs.<job_id>.with`. It returns `version` and `digest`, accepts only `push` or `workflow_dispatch` on `main`, embeds the exact CI jobs from `spring-ci.yml`, and deploys only after every selected check succeeds.

Production reads organization/repository variable `DOCKERHUB_NAMESPACE` and explicitly requires these named secrets: `DOCKERHUB_PUSH_TOKEN`, `PROD_HOST`, `PROD_USER`, `PROD_SSH_PORT`, `PROD_SSH_PRIVATE_KEY`, `PROD_KNOWN_HOSTS`, and `PROD_ENV_FILE`. The Docker Hub namespace is also the login identifier: use a matching account token, or an organization access token for an organization namespace. Callers use `secrets: inherit`; the called jobs select the caller repository's `production` Environment, whose values take precedence. `PROD_KNOWN_HOSTS` must be provisioned and verified independently. `PROD_ENV_FILE` is the complete candidate production environment content and must not define `IMAGE_REF`. Public input and path validation runs before CI without entering production. The publish job validates all Environment variables and secrets before its first registry request.

`compose-deploy.yml` is a separately callable deployment workflow with inputs `compose-file`, `health-timeout`, and `image-ref`, the five production Environment variables, and the six SSH/environment `PROD_*` secrets listed above. Callers must supply a digest from their verified publication run; the integrated production workflow supplies it directly. Do not invoke this workflow from a PR.

## Publication and recovery

The Gradle root project version is read from `./gradlew properties -q` without modifying the caller. A trailing `-SNAPSHOT` is removed, and only numeric `MAJOR.MINOR.PATCH` is accepted. Publication is serialized with `cancel-in-progress: false` by caller repository, image name, and resolved version. The Docker Hub repository must already exist and be public. Before publishing, the workflow checks both `prod-v<version>` and `sha-<full-commit>`; it accepts an existing pair only when their digests match and refuses conflicting or partial pairs. A new image is built and pushed once with Buildx, both immutable tags, OCI source/revision/version labels, `linux/amd64`, and a metadata file. The workflow requires both registry tags to resolve to the Buildx output digest before deployment.

Docker Hub immutable tags are required and are the registry-side protection against external writers. Before any push, the workflow reads the repository settings and accepts only all-tag immutability (an empty rules list, `.*`, or `^.*$`) or the exact RE2 rules `^prod-v[0-9]+\.[0-9]+\.[0-9]+$` and `^sha-[0-9a-f]{40}$`. Restricting the accepted forms avoids validating Docker Hub's RE2 rules with a different regex engine. Configure these settings outside the workflow; the workflow never mutates repository settings. The publish concurrency lock serializes this workflow's runs, while Docker Hub immutability prevents a different writer from replacing either release tag.

The remote Linux host needs Bash, `flock`, Docker Compose v2, and curl. The deployment directory must contain the currently configured production Compose file and `.env.prod`, but the legacy environment does not need `IMAGE_REF`. The workflow first looks for canonical `compose.yml`; when it is absent, it uses the basename of the caller's `compose-file` input, so an existing `docker-compose-prod.yml` can bootstrap safely. The named container must be running so its exact image ID can be captured. The candidate Compose must use `${IMAGE_REF:?IMAGE_REF is required}` for the target service. The SSH user needs access to that directory and Docker.

The workflow stages candidate configuration, locks the directory, and saves the original Compose file, environment, filename, and running container image ID before creating canonical `compose.yml`. It writes a run marker, pulls the digest, and runs `docker compose up -d --pull never --no-deps` for the target only. It verifies the exact candidate image ID, Docker health when present, and the local HTTP endpoint. On an error, only the marker owner restores the original Compose and environment and applies a temporary override to restart the exact saved image ID with `--pull never`; this prevents a service-level `pull_policy: always` from replacing or rejecting the saved local image. Rollback succeeds only after that image ID and health endpoint are verified. Rollback failure exits distinctly and remains visible to the caller. A successful deployment removes `.deploy-marker`; timestamped backups remain for operator recovery.

## Development

The production and deployment YAML contain generated copies of the scripts in `scripts/`; this lets private reusable workflows operate in the caller context without checking out this repository. After changing scripts or the CI jobs, run `node scripts/generate.cjs`, then `npm run verify`. The latter checks generated files and runs offline Node tests. Run `actionlint` and Bash syntax checks when available. Docker builds, external service integration, registry access and SSH deployment need their respective environments and must be validated separately.
